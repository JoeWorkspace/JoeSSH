## 1. 建议：先验证 30 天

目标：用现有 Store 产品，找出为什么目标用户会安装、完成真实 SSH 任务、下次还愿意使用。
先做一个小而完整的验证周期，再决定是否继续投入个人时间。

- 新增现金预算：0 元；不再设置域名、签名、招募补偿或工具采购预留。
- 建议工时：每周最多 6 小时，共 4 周；20 小时计划工作 + 4 小时缓冲 = 24 小时。
- T0 = 2026-09-12，D1–D30 为 09-12 至 10-11。D29–D30 使用已有缓冲，不额外排功能。
- 每周只有一个主要问题；每次决定下一步，都写出问题证据、工时上限和完成条件。
- 3–5 名自愿测试者是首批招募目标，不是市场成功的统计门槛。
- 若本人每周没有 6 小时，就减量或顺延；不为补计划挤占基本生活与主要收入时间。

Store 模式已隐藏 Mobile/Team 等预览表面。这些不再列为待开发功能。
历史后台快照证明已有访问和安装，但不代表当前活跃和收入，具体数值保存在本地私有工作记录。

09-15 版本核实：Partner Center 已上架的 Submission 7 只读包详情显示 1.1.27.0 x64，
文件名包含 `803fcef25b78` 和构建 `34593035494`，面向 Windows Desktop。
09-12 首连补丁是在这个已发布源码之上准备的后续修复，尚未发布，不能说当前 1.1.27.0 已包含它。
最新获客/使用汇总已存本地私有记录；报表提示浏览和安装数据延迟，使用统计标注“选择加入”，

这属于本机安装验收阻碍，不证明所有 Store 用户无法安装。保留旧副本和数据，未执行卸载或商店重置。

根目录 Git 已于 09-12 恢复，本轮只读健康检查通过；其 HEAD `d1ffb6c` 是历史内容比较基线，
工作区仍有大量既有改动，不能用根目录旧源码评价现售产品。无需重复恢复 Git。
新修复从已核实 canonical commit 的隔离 worktree 开展；来源核实也不能替代安装包和真实 SSH 验收。

首批用户假设：平时在 Windows 使用 SSH、拥有自有或授权 Linux 主机的个人开发者/运维者。
5–30 台主机只是可能的细分特征，不作为刚性门槛。
建议使用自己能长期支持的一种主要语言，并从一个已有可接触渠道开始。
今日数据支持优先观察“目标用户看完页面后是否愿意安装、具体顾虑是什么”；
愿意安装的人再进入真实首连观察。首次不愿安装也算有效反馈，不能强迫其完成连接后才计入样本。

## 3. 零预算具体意味着什么

| 工作 | 使用现有资源的办法 | 费用或资源不足时 |
| --- | --- | --- |
| 下载与产品介绍 | 现有 Store 页面；已有公开 README 如适用 | 不买域名，不新建营销平台 |
| 商店数据 | 已有 Partner Center 可用报表 | 缺少字段标未知；用自愿测试补充，不购买分析服务 |
| 反馈 | 现有 Issue、已有邮箱或用户自愿交流渠道 | 不付费招募，不购买客服系统 |
| 使用记录 | 本地一张 Markdown 表；匿名编号 | 不新建遥测服务器、不做用户指纹追踪 |
| 截图与教程 | 现售包截图、现有录屏工具；先一份简短指南 | 没工具就用文字，不购买素材或设计服务 |
| 构建与验证 | 现有设备和可用工具；既有无需额外费用的运行额度 | 额度不足先等待或推迟更新；不付费扩容 |
| SSH 测试 | 已有自有/授权主机；受试者操作自己的主机 | 不租云服务器，不替用户开通资源，不为赶任务绕过主机核验 |

已有工具、CI、AI、托管、存储和试用额度不能默认无限或免费；执行前核对是否产生新增费用。
不购买订阅、充值 API、付费扩容，不开启会产生新账单的服务。已有付费账号的续费也是实际现金需求，
不能藏在“已有资源”里；若任务依赖付费续期则改方案或暂停，不擅自更改用户账户。
零新增现金不等于零成本：个人时间、现有设备及日常网络仍有成本，不据此宣称商业已盈利。

## 4. 第一个月的周计划

每周计划 5h，预留 1h。工时是上限估计，不是要求每项用满。
本周期不承诺更新次数；必要测试超过可用工时就顺延，不能为了零预算跳过验证。

| 周次 | 计划任务（5h/周） | 交付物与完成条件 |
| --- | --- | --- |
| W1 | Store 现状记录 0.5h；可用后台数据 1h；现售包自测 1.5h；源码映射只读检查 1h；记录与邀请草稿 1h | 一页基线；现售版本、主任务、未知项清楚；未能映射不写成已核对 |
| W2 | 通过一个渠道招募 1h；最多三次短体验观察及异步反馈 2h；按证据准备一个页面/指南改进草稿 1h；记录和安排回访 1h | 争取累计 3–5 人自愿参加；先看安装意愿和原因，再观察愿意者的首连，保留拒绝安装、失败和退出 |
| W3 | 一个已复现阻碍的修复与相关验证 3h；用户复测 1h；记录与后续安排 1h | 若是文案问题只改文案；若没有共同阻碍就继续观察；超过工时则缩范围或延后 |
| W4 | 必要验证/更新准备或继续调查 2h；成熟 R7 回访 1.5h；购买理由探索 0.5h；月度决策 1h | 一项明确结论：继续一个小周期、换用户/渠道、社区维护或暂停新增工作 |

额外共 4h 缓冲用于故障、支持、测试返工和 D29–D30 总结，不预先承诺给新功能。
访谈和支持占用本人时间，也计入 24h；发现严重安全/数据损失问题时优先处置，
暂停招募或其他任务，不强迫在 3h 内草率发布修复。
新的代码或商店资料提交，在相应执行阶段完成审查和发布验证；本轮执行未发送对外消息或提交商店更新。
已确定的首连缺陷可提前修复，不必等到 W3；修复、验证及本人复核时间仍计入本周期，不另加功能额度。
已复现缺陷的发布取决于来源、必要测试和安装包验收；不以用户付费意愿或达到复用人数为前提。

## 5. 先查哪个问题，再做哪个动作

| 实际观察 | 下一步最小动作 |
| --- | --- |
| Store 可用数据表明曝光少 | 明确描述关键词和用途，在一个允许相关分享的社区发一次具体使用案例 |
| 有访问但获取少 | 先核对首屏描述、截图、适用平台和限制；只修改一项并留前后记录 |
| 已启动但无法连接 | 看受试者卡在哪一步；修首连、说明或一个确定的兼容问题 |
| 能使用但不再回来 | 问是没有任务、仍用旧工具，还是 JoeSSH 没有额外价值；不自动加功能 |
| 主动回来并反复提同一需求 | 估算一个小改进是否能在下一周期完成；不直接扩成 Pro 或云服务 |
| 没拿到数据或招不到人 | 标“尚未验证”；调整一次文案或渠道，控制继续投入的时间 |

获客渠道先选自己已经有接触能力的一个，例如现有用户的自愿反馈、已有同行关系、
或允许产品交流的相关社区。只有第一个渠道投入了约定工时仍不适合，才换第二个。
助手已准备[邀请、15 分钟观察与回访材料](zero-budget-validation-kit.md)；
对外发帖、私信和邮件由开发者执行或在后续明确授权后进行。
不批量骚扰、不买流量、不索要好评，不承诺奖品、免费代运维或无限支持。

一次邀请草稿：
> 我做了一个已经上架 Microsoft Store 的 Windows SSH 工具 JoeSSH。
> 想找平时使用 SSH 的朋友自愿试一次真实任务，告诉我安装或连接最卡的地方。
> 不需要提供密码、私钥或服务器信息，也不要求评价；你按自己的时间决定是否参加。

观察时让用户自己操作自有或授权主机。先不提示；求助后可协助解释，但记录“协助完成”。
全员只要求首次真实任务与下次使用反馈；SFTP、转发按他们的实际需要测试。
不把整个七项功能清单强加给只想开一个终端的测试者。

## 6. 只记录能帮助决策的数据

采用[单页工作记录](solo-plan-working-templates.md)，日常无需填写 v2 的全部指标和模板。

- Store 汇总：记录后台实际字段、原始单位、窗口、地区和来源；缺项为未知。
  获取不等于安装，安装不等于活跃；不跨窗口相除制造转化率。
- 受试者：一个匿名编号对应一人，记录来源、现售版本、是否安装、是否真实成功、
  是否独立完成、卡住步骤与支持分钟。资料未准备、放弃、失联都保留。
- 再次使用：首次成功后第 7–13 天内至少一次自主真实使用记为 R7。
  到第 13 天结束才进入完整观察分母；其余记未成熟。回来是完成自己的任务，
  不把为了配合测试重复点击或开发者演示算成自主复用。
- 报告先写人数，例如“4 人满观察期，2 人确认再用，1 人未用，1 人未知”；
  小样本不声称稳定留存率，也不外推为所有 Store 用户的数据。
- D30 本月可能观察不完整；后续仅在激活后第 28–34 天窗口结束后统计。
  不为赶 30 天计划提前宣布长期留存。

原始联系方式与编号分开存放，笔记留本地私有位置，不进入公开仓库。
不要求用户提交主机地址、凭据、命令内容、日志或终端输出。
前后改商店资料不是随机试验；记录实际生效日，至少留一个可比观察窗口，
流量很小时以用户任务观察为主，不编造增长百分比。

## 7. 月底怎样判断值不值得继续

本周期没有硬性的 30 激活/10 同需求要求。旧门槛仍是后续商业假设，不是本月必须完成的作业。
减少本轮目标不表示那些商业门槛已经通过，也不意味着几个人说好就能直接开售。

- 有人独立完成并主动再用，能说清具体用途：值得再用同样上限做一个小周期。
  例如 3–5 人中有 2 人确认自主回来，是进一步研究的信号，不是 PMF 证明。
- 能完成但没有复用：先区分没任务、失败、已有工具更好和失联；查原因后再投开发时间。
- 一位用户发现明确缺陷：即使没有重复样本也可修真实缺陷；新功能则需要更强的共同需求。
- 没有样本：只说明渠道/招募未验证；本月工时用尽就停止追加，先决定是否值得换一个渠道。
- 两个有工时记录的小周期仍没有有效反馈或复用理由：转为必要维护，暂停新增开发。
- 支持占满预留：先暂停招募，不许通过承诺额外免费服务换来使用量。

如果一项更新的来源、验证或发布费用无法在既有资源内解决，就继续维护现售版的说明与反馈，
不发布未经验证的包，不绕过现有安全/发布检查，也不购买新服务顶上去。

## 8. 赚钱放在哪一步

首月可以问“你为什么愿意买”，不必等到某个用户数量才能讨论需求。
但不预先建设 Pro、许可证服务器、账号体系、订阅或 Hosted Sync。
现在免费产品已有 Store 分发，第一步是找到别人反复需要的结果；免费上架本身不会产生销售收入。
canonical 源码已有自愿支持作者页面，无需再建设一个赞助入口；本轮未核实实际到账与收款适用条件。
“尚未读取收入”不能写成“确定收入为零”，支持作者也不能当成付费功能需求已经成立。

后续仅评估一种路径：
1. 用户想自愿支持：若已有可用且核验过的收款路径，可另行评估支持入口；
   支持作者和购买功能分开统计，不承诺未做的付费权益。
2. 用户愿买一个明确的本地增量：先核对既有能力、实现和售后工时，
   再比较适用 Store 付费能力或外部收款条件。不预设现有包支持内购，不提前注册收费服务。
3. 用户愿为一项有限的配置说明/迁移咨询付费：单独计算本人交付工时，
   不把咨询收入当软件订阅验证，不默认代操作生产系统或保管凭据。

只有明确的交付、个人账户/地区与产品资格、退款/税费安排、正的单笔贡献，
并且不需先垫付现金，才值得另定小额试卖计划。本轮不启用收费、不收预售款。
若必须采购、充值、垫付测试款或支付固定费用，零预算条件下先暂停该路径。
按订单扣取的渠道费用、退款和税费仍然是真实成本，不称“完全免费收款”；
未来赚到钱也不自动授权再投入。

保留已有 MIT 权利和免费 Community 的产品承诺。MIT 允许收费，但不能通过撤销旧权利制造购买理由。
若本人急需当月稳定收入，JoeSSH 仍是尚待验证的产品，不能作为可靠收入预测；
应给它上述有限时间，而不继续无限投入等待免费安装自然变成付费。

## 9. 本月暂缓的范围

不新增 Mobile、托管 Sync、企业权限/SSO、AI、多平台发布矩阵、新协议、付费广告、
新官网、复杂埋点和大规模重构。已有功能和数据不因规划收敛被删除，
存量支持范围内的安全与兼容问题继续处理。

完整性只需要四件事：一个待验证的问题、一个时间上限、一份真实证据、一个下一步决定。
本版已将工作量和新增现金要求压到个人可试的范围，能否盈利仍需用户和交付证据。
