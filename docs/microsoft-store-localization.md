# Microsoft Store Localization Draft

This is the draft listing package for JoeSSH `0.1.0-beta.18`. The machine-readable
manifest is [localization-manifest.json](assets/microsoft-store/localization-manifest.json)
and is generated by `scripts/generate-microsoft-store-localization.mjs`.

The package contains 80 Store discoverability locales. Store listing language is
separate from installed application UI language: a Store listing does not claim
that JoeSSH has a translated UI for that locale. The manifest remains
`draft-not-submitted` and is not a Partner Center upload or API payload.

## Product Facts

Every listing is constrained to the current product baseline:

- JoeSSH is free, open source under MIT, and a Windows x64 Public Beta.
- The product is local-first SSH with host-key review, an interactive terminal,
  SFTP, and local port forwarding.
- Profiles and preferences stay on the device by default.
- No JoeSSH account or hosted service is required.
- No listing claims publication, certification, paid features, or telemetry.

The product title is always exactly `JoeSSH`. Descriptive positioning belongs in
the short description and localized keywords.

## Technical Fact Audit

An AI-assisted technical-fact and negation audit covered all 80 locales. It
found no high-confidence loss or reversal of the authorized-server, 25 MiB,
loopback-only, device-local, no-account, or no-hosted-service facts. This audit
is not native-language review or approval.

The draft checker mechanically protects only stable technical tokens and the
recorded localized aliases: `SSH`, `SFTP`, `Windows`, `x64`, Public Beta,
`JoeSSH`, the `25 MiB` size forms, and `loopback`/Afrikaans `teruglus`/the
Quechua `Loopbacklla` form. It does not claim to mechanically prove translated
negation, grammar, terminology, or native-language quality.

## Locale Model

`locale` is the canonical BCP 47 value. `storeLocale` is the Microsoft/Windows
Store value from the reviewed draft allowlist. Script-qualified Chinese values
and the Microsoft Quechua value remain distinct from their canonical BCP 47
values:

| Canonical BCP 47 | Store value  | Status                                                 |
| ---------------- | ------------ | ------------------------------------------------------ |
| `zh-CN`          | `zh-Hans-CN` | Existing `zh-hans-cn` listing code observed in the configured listing |
| `zh-TW`          | `zh-Hant-TW` | Exact code confirmed in the full Partner Center export |
| `qu-PE`          | `quz-PE`     | Exact Peru code confirmed in the full Partner Center export |
| `mk-MK`          | `mk`         | Partner Center exports Macedonian as the bare `mk` code |

The live Partner Center **Add languages** dialog exposed 830 options. All 80
target labels and unique language IDs were observed; the bounded dialog
evidence is recorded in
[partner-center-language-options.json](assets/microsoft-store/partner-center-language-options.json).
The complete 80-locale export is recorded in
[partner-center-export-1152921505701586331.csv](assets/microsoft-store/partner-center-export-1152921505701586331.csv)
with SHA-256 `5fca727e00dd47c457ddab8ddcbda318c1464427ff3af02ca921a48981e375bf`.
It confirms the exact import code for every target locale, including `mk` for
Macedonian, `zh-hant-tw`, and `quz-pe`.

Four entries retain `reviewRequired: true` for mapping or source-name decisions:

- `kn-IN`: Partner Center resolves the supplied source name to Kannada (India),
  language ID 52; native review is still required.
- `qu-PE` / `quz-PE`: Quechua (Peru), language ID 147, is selectable and its

- `es-MX`: Partner Center has no generic Latin America option, so Spanish
  (Mexico), language ID 66, is the explicit regional choice.
- `ca-ES-valencia`: Valencian, language ID 117, is selectable and its variant

These four entries remain `reviewRequired: true`. The Quechua copy is a
consistent draft, not a native approval.

## Store/UI Separation

The 15 shipped UI packs remain the only UI packs:

`zh-CN`, `zh-TW`, `en`, `ja`, `ko`, `es`, `fr`, `de`, `pt-BR`, `ru`, `ar`,
`hi`, `id`, `vi`, and `th`.

The Store manifest truthfully maps these packs to the regional listings that the
resolver supports, including shared mappings:

- `en-US` and `en-GB` -> `en`
- `es-ES` and `es-MX` -> `es`
- `pt-BR` and `pt-PT` -> `pt-BR`

The remaining Store locales are discoverability-only. They may be added as
Store listings after native review without claiming complete installed UI
coverage. Every submitted listing still needs its own reviewed screenshots.

## Review State And Readiness

Every entry has one of these explicit statuses:

- `translation-draft`: generated structural draft; not submit-ready.
- `native-reviewed`: a native-language reviewer and provenance record exist.
- `native-approved`: an approval record exists for submission.

The current 80 entries are intentionally `translation-draft`. The draft
validator can pass structural checks, but submission readiness fails closed until
every locale has native review provenance, a reviewed screenshot URL, a bound
product source commit, and confirmed Store locale values.

## Validation And CSV

Run the draft checks:

```powershell
node scripts/generate-microsoft-store-localization.mjs
node scripts/check-microsoft-store-localization.mjs
npm run test:windows-store-localization
```

The generator derives `generation.sourceState` from the current Git worktree.
For a reproducible fixture or clean-clone byte comparison, pass the reviewed
state explicitly with `--generation-source-state=clean-working-tree` or
`--generation-source-state=dirty-working-tree`; the override is validated
against the finite evidence enum and does not change the actual product source
binding.

Generate a strict draft CSV template with `Title`, `Description`,
`ShortDescription`, `Feature1..Feature5`, and `Keyword1..Keyword7`:

```powershell
npm run generate:windows-store-listing-csv
```

The CSV includes canonical and Store locale columns and contains no fabricated
asset URLs. `--require-ready` makes the generator fail if submission readiness
is not met:

```powershell
node scripts/generate-microsoft-store-listing-csv.mjs --require-ready
```

The deterministic native-review handoff is [native-review-handoff.csv](assets/microsoft-store/native-review-handoff.csv).
It is generated from the manifest and includes one row for each of the 80
locales, a content SHA-256, and blank `Reviewer`, `ReviewedAt`, `Provenance`,
and `ScreenshotEvidence` columns. Generate or verify it with:

```powershell
npm run generate:windows-store-native-review-handoff
```

Native reviewers fill those four evidence columns and the review status in a
separate controlled review step. A human must then verify the locale mapping,
review provenance, and screenshot URLs before copying approved values back into
the manifest. The handoff generator never infers or fabricates that evidence.

After a human has completed the handoff, apply it only to an explicitly named
JSON output path:

```powershell
npm run apply:windows-store-native-review-handoff -- --handoff=C:\path\native-review-handoff.csv --output=C:\path\reviewed-manifest.json
```

The intake parser requires the exact 80-row tracked content baseline, canonical
locale/store mappings and content hashes, `native-reviewed` or `native-approved`
status, reviewer/provenance/timestamp fields, and structured screenshot evidence
(`urls`, `reviewer`, `reviewedAt`, `provenance`) with HTTPS URLs. It rejects BOMs,
control characters, formula-injection cells, malformed CSV, duplicate or unknown
locales, and content drift. It always reads the tracked manifest as its baseline,
refuses to overwrite `localization-manifest.json` or any existing output (including
case, symlink, and hardlink aliases), and writes only review status, native review,
and screenshot assets to the explicit output JSON. The output is created with
exclusive-write semantics, validated before and after writing, and remains
`draft-not-submitted`; it is not a Partner Center submission payload.

Once native review, screenshot evidence, candidate-source binding, and a
checksum-bound full Partner Center export are all present in that reviewed
manifest, merge it into an official Partner Center listing export:

```powershell
npm run generate:partner-center-listing-import -- --template=C:\path\partner-center-export.csv --manifest=C:\path\reviewed-manifest.json --output=C:\path\partner-center-import.csv
```

The importer preserves unsupported template fields, replaces the reviewed
listing fields, requires and writes all 80 locale columns (including
`zh-hans-cn` and `zh-hant-tw`), accepts the official BOM and quoted multiline
cells, and uses an exclusive output write. It computes the SHA-256 of the exact
template bytes and compares it with `storeLocaleCatalog.exportSha256`; it never
invents missing locale columns. It fails closed if any submission-readiness gate
is missing, if template field IDs drift, if an unexpected or missing locale is
present, if the export hash does not match, or if the output would overwrite an
input or existing file. The current tracked draft is intentionally rejected.

Draft validation also performs mechanical Unicode normalization and control-code
checks, expected-script checks for non-Latin listings, cross-language paragraph
duplicate checks, CSV formula-injection checks, and a `known translation error
markers` gate for recorded forbidden substrings and exact listing-field values.
These checks only protect structure and export safety; they are not a
native-language review.

Assets are modeled as `listing.assets.screenshotUrls` plus an explicit
`screenshotBinding`. Empty URLs are valid draft state only; submission readiness
requires at least one reviewed HTTPS screenshot URL for every locale.
